# 前额叶训练场 · 设计与交接文档

> 本文档是项目的唯一权威文档。任何人接手开发，读完本文即可继续。
> 最后更新：2026-08-25（v1.2：hub + 4 个已实现游戏 + 6 个规格待实现）

## 1. 项目定位与理念

### 是什么

- 工作名：PrefrontalCortexGame（前额叶训练场）
- 类型：移动端认知训练小游戏合集
- 形态：一个 hub 首页 + 10 个独立小游戏，**用户自己选择玩什么**
- 引擎：Godot 4.7+，纯 GDScript，无外部依赖，竖屏 720×1280 基准

### 核心理念（不可妥协的三条）

1. **每个游戏只练一种执行功能。** 前额叶管执行功能（自控、专注、计划、决策、抑制冲动）。每个游戏直接对应一个认知科学里真实存在的任务范式，练的就是那个范式练的东西，不混装。
2. **诚实标注。** 游戏只练「该能力在游戏内的熟练度」，不承诺迁移到现实、不承诺变聪明。神经可塑性需要数周数月；游戏提供的是「练习场」，不是「修复」。
3. **拒绝营销话术。** 文案中禁用：「3 分钟修复大脑」「激活 CEO」「多巴胺戒断」「变聪明」「左脑右脑开发」。每个游戏入口用一句平实的功能描述（如「抑制控制 · 干扰」）。

### 认知科学依据（选型来源）

| 执行功能 | 有依据的范式 | 不采用的流行说法 |
| --- | --- | --- |
| 抑制控制 | Stroop、Go/No-Go、Stop-signal | —— |
| 注意 | 舒尔特方格、多目标追踪（MOT） | 「专注力音乐」 |
| 工作记忆 | N-Back、瞬时计数（subitizing） | —— |
| 认知灵活性 | 任务切换范式 | —— |
| 自控 | 延迟折扣（棉花糖实验） | 「多巴胺戒断」 |
| 计划 | 汉诺塔（Tower of Hanoi） | —— |

正念、睡眠、运动对前额叶最有效但属于生活干预，做不成街机机制，**不在游戏清单内**。

## 2. 架构

### 结构总览

```text
prefrontal-cortex-game/
├── project.godot     # main_scene = scenes/Hub.tscn；竖屏 720×1280
├── scenes/           # 每个场景只有根 Control + 脚本，节点树全部由代码构建
│   ├── Hub.tscn
│   ├── Stroop.tscn
│   ├── Schulte.tscn
│   ├── Dots.tscn
│   └── GoNoGo.tscn
├── scripts/
│   ├── GameBase.gd   # 所有游戏继承的脚手架
│   ├── Hub.gd        # GAMES 数组 = 游戏注册表
│   ├── Stroop.gd
│   ├── Schulte.gd
│   ├── Dots.gd
│   └── GoNoGo.gd
└── docs/design.md    # 本文档
```

### 架构决策

- **场景文件只是壳。** .tscn 里只有 `Control` 根节点 + 脚本引用；所有 UI 节点在 `_ready()` 里用代码构建。这延续了同仓库 DodgeShotLab 的做法，避免编辑器二进制状态和代码漂移，diff 干净。
- **GameBase 提供公共外壳。** 深色背景（`#0d1220`）、左上角「< 返回」、居中标题。子类只需设置 `title_text`（在 `_init()` 里）并重写 `_build_game()`。
- **Hub 用数据驱动注册。** `GAMES` 数组是唯一注册点：`{title, func, group, scene, built}`。列表按 `group`（执行功能）分段；卡片两行（游戏名 + 练什么）。未实现的游戏 `built: false` → 置灰并在右侧标「即将推出」，功能说明仍可见；实现后翻成 `true` 并填 `scene` 路径即可。
- **游戏间零耦合。** 每个游戏一个场景 + 一个脚本，返回即 `change_scene_to_file` 回 hub，无共享运行时状态。本地成绩各自存 `user://*.cfg`。

### 代码规范（沿用本仓库惯例）

- GDScript，`class_name` 不使用，场景脚本用 `extends` + 文件名即类
- 每个函数前一行 `##` 文档注释（DodgeShotLab 风格）
- 常量全大写、`const`，可调数值集中在脚本顶部
- 颜色统一十六进制 `Color("#rrggbb")`；共享调色板见 §6
- 中文界面文案（按钮、状态、标题），代码注释可中可英
- UI 节点代码构建时用 `set_anchors_and_offsets_preset` 做锚点布局，位置类用固定像素（竖屏基准 720 宽）

## 3. 如何新增一个游戏（五步）

以「N-Back」为例：

1. **写脚本** `scripts/NBack.gd`：

```gdscript
extends "res://scripts/GameBase.gd"
## N-Back：判断当前刺激是否与 N 步前相同。


const LIVES := 3

var score := 0

func _init() -> void:
    title_text = "N-Back"

func _build_game() -> void:
    # 构建 HUD、主内容、按钮，并开始第一试次
    pass
```

2. **建场景** `scenes/NBack.tscn`（内容三行，照抄改 id 和脚本路径）：

```text
[gd_scene load_steps=2 format=3]

[ext_resource type="Script" path="res://scripts/NBack.gd" id="1_nback"]

[node name="NBack" type="Control"]
script = ExtResource("1_nback")
```

3. **注册进 hub**：`scripts/Hub.gd` 的 `GAMES` 数组里找到对应条目，填 `scene` 路径、`built: true`。
4. **headless 验证**：

```bash
GODOT="/Applications/Godot.app/Contents/MacOS/Godot"
PROJ="<项目路径>"
"$GODOT" --headless --path "$PROJ" res://scenes/NBack.tscn --quit-after 5 2>&1 | grep -iE "error|invalid|failed|nonexistent|cannot|parse"
```

   无输出 = 通过。（经验：`add_theme_font_color_override` 不是真实 API，正确的是 `add_theme_color_override`。）
5. **肉眼验证 UI**：编辑器 F5，进游戏点几轮，确认布局、反馈、返回。

## 5. 各游戏规格

### 5.1 反向色字 Stroop ✅ 已实现

**玩法**：中央显示一个颜色字（如「蓝」字但字体是红色），点「字体颜色」对应的按钮，抑制「字义」的自动反应。

**已实现规格**（`scripts/Stroop.gd`）：

- 颜色集合：红 `#ff5d73` / 蓝 `#5d9bff` / 绿 `#4ade80` / 黄 `#ffd75d`，2×2 按钮；按钮填色 + 写颜色名（双编码，照顾色盲）
- 一致试次（字义=颜色）与冲突试次（字义≠颜色）混合；冲突概率初始 30%，每答对 +3%，上限 65%
- 每试次限时 2 秒，倒计时条（底槽 + 填充，剩余 <25% 变红）；超时视同错误
- 试次间隔 0.35s：答对/点错/超时后锁输入，避免连点吃掉下一题；超时不会在同一帧连扣生命
- 常显提示「点的是颜色，不是字」；答对显示加分，点错/超时分别提示
- 计分：答对 10 分 + 剩余秒数×5 速度分 + 连击加成（每连击 +2，封顶 +20）
- 生命 3 次，错误/超时扣 1 并断连击；归零结束，可重开；本地存 `user://stroop_best.cfg`
- 参数集中在脚本顶部 `const`，可直接调

**已知的后续调优点**：冲突比例 30%→65%、速度分是否诱导乱点，仍待实玩验证（见 §8）。

### 5.2 舒尔特方格 Schulte ✅ 已实现

**玩法**：5×5 网格随机 1–25，按顺序点击，越快越好。

**已实现规格**（`scripts/Schulte.gd`）：

- 首次点击开始计时；点对该格绿色闪一下再禁用，点错计数 + 红色闪烁（不中断流程）
- HUD 常显「下一个 N／25」；点错过才附加失误次数
- 格子边长按窗口可用空间计算（56–120px），重开按钮跟在网格下方；窗口拉伸会重排
- 完成显示用时 + 失误数 + 是否新纪录；本地存 `user://schulte_best.cfg`
- 「重新开始」按钮随时可重排

### 5.3 看点数 Dots ✅ 已实现

**玩法**：屏幕短时间闪现随机分布的若干圆点，消失后用数字键盘输入看到的点数。

**已实现规格**（`scripts/Dots.gd`）：

- 一局 60 秒街机倒计时（开局 1 秒「准备」不扣时间），时间到结束；本地存最佳分 `user://dots_best.cfg`
- 点数 4–12 起步；答对先把闪现时间从 0.6s 每次 −0.02s（下限 0.35s），触底后点数上限 +1，不封顶；答错反向降难度
- 计分：正好 10 分 + 连击加成（每连击 +2，封顶 +20）；误差 ±1 给 5 分（半分，不升难度、不断连击）；误差 ≥2 断连击并降难度
- 点位用 Bridson 泊松盘，保证画出的点数 = 题目数量；半径随数量收缩（8–18px）
- UI：圆角卡片 + 闪现进度条；底部 0–9 + 删除 + 确定，非输入阶段键盘变淡；桌面可用键盘数字/退格/回车；面板和键盘随窗口重排
- 反馈阶段短暂回显圆点，方便对照实际数量

### 5.4 反向反应 GoNoGo ✅ 已实现

**玩法**：屏幕陆续出现彩色圆。默认「绿圆→点它，红圆→别点」。连续答对 10 次后规则反转（红点绿停），顶部色块同步改动词。

**已实现规格**（`scripts/GoNoGo.gd`）：

- 刺激最多显示 1.0s，未反应即过；试次间隔 0.9–1.4s 随机；开局 1 秒准备
- Go 试次 75%；连续 4 个 Go 后强制一个 No-Go，避免一直连点
- 计分：Go 命中 +10；No-Go 忍住 +15；误点 No-Go 或 Go 没点到都扣 1 命并断连击
- 生命 3 次，归零结束；本地存 `user://gonogo_best.cfg`
- 刺激弹出时圆和底部「点」按钮微微放大；非刺激阶段按钮变淡；桌面可用空格/回车
- 顶部常显规则色块：绿/红底上写「点」或「停」

**已知的后续调优点**：间隔 0.9–1.4s 偏稳，若觉得「痒」不够可把 `GAP_MIN/MAX` 下调。

### 5.5 红灯停 StopSignal（待实现，规格）

- **玩法**：每轮一辆小车从左向右驶向终点线，玩家本能任务是「车到线前点一下加速/收集」。但车行驶途中可能突然亮红灯——亮了就必须**不点**。已启动的动作要急刹。
- **数值建议**：行驶时长 1.2–2.0s 随机；25% 的轮次在行驶 40%–70% 进度处亮红灯；红灯亮后 0.5s 内点了即失败。
- **计分**：正常到达 +10；红灯成功忍住 +20；红灯没忍住扣生命。
- **要点**：与 GoNoGo 的区别要在手感上拉开——这游戏有连续动作进度条（车在动），玩家全程处在「准备点」的状态，抑制的是**进行中的冲动**。实现上就是个 AnimatedSprite/位置插值 + 随机红灯。

### 5.6 N-Back（待实现，规格）

- **玩法**：序列呈现刺激（首版用 3×3 宫格里亮起的位置），玩家判断「当前位置是否与 N 步前相同」，两个按钮：「相同」/「不同」。
- **数值建议**：N=2 起步；刺激间隔 2.5s（认知负载的标准节奏，别太快）；连续答对 10 个升 N（封顶 N=4），连错 3 个降 N。
- **计分**：答对 +10；答错扣生命；「相同」试次占 30%（低了玩家会全按「不同」刷分）。
- **要点**：开始前 N 步不判分；HUD 必须常显当前 N 值和进度。刺激通道可扩展为位置/颜色/声音三通道混合（混合就是 Dual N-Back 方向，留作后续版本）。

### 5.7 任务切换 Switch（待实现，规格）

- **玩法**：屏幕中央出现一个数字（1–9，非 5），上方随机显示当前规则：「奇偶」或「大小（>5 / <5）」。玩家按当前规则点对应按钮。
- **数值建议**：规则每 2–4 试次随机切换；切换试次的比例约 40%。
- **计分**：重复试次（规则没换）答对 +10；切换试次答对 +20（切换成本是认知科学的经典指标，切对了说明换挡成功）；答错扣生命。每试次限时 3s。
- **要点**：规则标签要做成醒目的颜色块（奇偶=蓝系，大小=橙系），玩家靠颜色余光即可知道当前规则，不必每次读字。

### 5.8 追踪异色球 Track（待实现，规格）

- **玩法**：开始时若干球中混着 1–3 个异色球（高亮显示 1.5s 让玩家记住），随后所有球变同色并开始移动，几秒后停下，玩家点出「刚才哪些是异色球」。
- **数值建议**：球总数 6–12；异色球数随难度从 1 升到 3；移动时长 4–8s；球速度适中且互相反弹（边界反弹 + 球间碰撞可以简化为不处理，只要轨迹够乱）。
- **计分**：全对 +20；多选/漏选各 −1 生命或只给部分分。答对轮次 +1 球数（封顶 12）。
- **要点**：这是 10 个里视觉实现最重的（多球运动 + 反馈），用 `_process` 更新位置数组 + `_draw()` 画圆即可，不需要物理引擎。高亮阶段务必足够醒目（描边脉冲动画）。

### 5.9 延迟满足 Marshmallow（待实现，规格）

- **玩法**：每轮开始给一个小奖励选项：「现在拿 10 分」或「等待 X 秒拿 3 倍」。等待期间屏幕有进度条，但**等待有 20% 概率失败归零**（风险来自等待本身）。玩家随时可中途放弃，拿到部分分。
- **数值建议**：等待时长 5–15s 随机；失败概率随已等待时间上升（前 3 秒 0%，之后每秒 +4%，制造「早等早踏实」还是「再赌一把」的拉扯）。
- **计分**：一局 10 轮，总分就是延迟决策能力的直接读数。
- **要点**：这是 10 个里唯一的「决策」而非「反应」游戏，节奏刻意放慢。失败时的反馈要戏剧化（分数碎裂动画）但不要惩罚性音效，避免训练成「赌徒」心态——文案强调「策略」而非「运气」。

### 5.10 汉诺塔 Hanoi（待实现，规格）

- **玩法**：经典规则，3 柱 N 盘，把全部盘从左柱移到右柱。点选柱子两次（来源→目标）完成一次移动，非法移动（大盘压小盘）抖动提示。
- **数值建议**：从 3 盘开始，完成且步数 = 最优（2^N −1）则下一局 +1 盘，封顶 6 盘（63 步已是很大的计划量）。步数超最优 ×1.5 仍可通过但标记「非最优」。
- **计分**：过关基础分 N×30；最优步数额外 N×50；用时可显示但首版不参与计分（汉诺塔练的是计划不是速度）。
- **要点**：实现要点在交互状态机（选中态高亮 → 目标柱预览合法性）和盘的动画（tween 抬起/平移/落下）。这是 10 个里状态管理最复杂的，所以放最后。

## 7. 验证流程（每个游戏合入前）

1. headless 跑场景无报错（命令见 §3 第 4 步）
2. F5 实跑：完成至少一整局、故意输一局、返回 hub 再进（验证场景切换无残留）
3. 检查 hub 按钮状态与 design.md 总表状态同步

## 8. 首版待验证问题（产品层面）

- Stroop 冲突在实时压力下是「可玩的张力」还是「容易点错的挫败」→ 挫败则降爬坡速度或加试次间隔
- 一致/冲突混合比例的甜点区间（当前 30%→65%）
- 速度分是否诱导乱点（若是：错误惩罚改为 −10 分）
- 10 个入口玩家是否看得懂各练什么（hub 已按执行功能分组 + 两行卡片常显「练什么」；若仍不够再加一句话说明页）
- 合集的整体留存动力：纯自选是否足够，还是需要「每日一练」轻结构（留到 10 个全齐后再评估）

## 9. 明确不做（当前版本）

- 账号系统、云同步、排行榜对战
- 正念/呼吸类内容（生活干预，不是街机机制）
- 「脑年龄」「智商分」这类量化包装（违反诚实原则）
- 提醒通知、打卡系统（先验证游戏本身是否好玩）
